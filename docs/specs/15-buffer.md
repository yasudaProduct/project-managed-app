# バッファ管理仕様書

> **ステータス：設計確定・未実装**
> 本書は、プロジェクト管理におけるバッファの定義と、このシステムでの取り扱いを定める。現行の実装（`docs/specs/02-evm.md` の「9. バッファの取り扱い」）とは異なる。差分は「13. 現行実装との差分」にまとめる。
> 現行システムとの対応付け（既存データの移行、Excel同期との関係など）は未決であり、「12. 未決事項と将来機能」に挙げる。

## 1. 概要

### 目的

バッファを「見積もりの不確実性に備える、根拠のある予備」として扱い、その減り方をプロジェクトの危険信号として使えるようにする。

次のような使われ方を防ぐことも目的とする。

- 根拠のない数字（例：利益率の調整のために積む工数）がバッファとして扱われる
- タスクの超過がバッファで黙って吸収され、実行中に見えない
- バッファの数字が後から書き換えられ、判定が理由なく変わる

### 適用範囲

- バッファは **WBS単位** で持つ（現行のEVMと同じ単位）。1プロジェクト1WBSの運用では、プロジェクト全体に1つとなる。
- 扱うのは **工数のバッファ** である。金額は工数から換算して表示する（10章）。
- 期間（納期）のバッファは扱わない（将来機能）。

## 2. バッファの定義

> **バッファ**とは、見積もりのブレと特定済みのリスクに備えて、タスクの見積もりとは別枠で確保する工数である。PMが管理し、取り崩しや解放は記録する。その減り方を進捗と比べて、プロジェクトの危険信号として使う。

### 対象外

| 対象外のもの | 扱い |
|---|---|
| 利益 | バッファではない。使わずに余ったバッファが最終的に利益に戻ることはあるが、バッファの大きさを利益目標から決めてはならない |
| スコープの追加 | 変更管理で予算そのものを変える（8章）。バッファからは払わない |

### 似ているが異なるもの

| 概念 | バッファとの違い |
|---|---|
| サバ（水増し） | タスクの見積もりに隠れて分散しており、管理も監視もできない |
| フロート（余裕日数） | 工程のつながりから結果的に生まれる余裕で、意図して置いたものではない |
| 管理予備 | 合意した範囲の中で起きる想定外の作業への備え。使うには上位者の承認が要る。本システムでは当面持たない |

### 予算の構造

```
売価
├ 原価予算（決裁額）
│  ├ BAC        … WBSのタスクに割り当てた基準工数（EVMで進捗を測る対象）
│  ├ バッファ   … PMが管理する予備（見積もりのブレ・特定済みのリスク）
│  └ 管理予備   … 想定外への予備（本システムでは当面持たない）
└ 利益
```

## 3. 用語定義

| 用語 | 定義 |
|---|---|
| 明細 | バッファの大きさの根拠となる単位。種別は「リスク」と「比率」の2つ |
| 確保量 | バッファとして確保した工数。当初確保量 ＋ 追加累計 |
| 当初確保量 | バッファ計画の確定時点の、明細の確保量の合計 |
| 追加 | 決裁変更を経て確保量を増やす操作 |
| 取り崩し | バッファから工数を移して、新しいタスクを追加する操作 |
| 解放 | 見直しの結果、不要になったバッファを落とす操作 |
| 超過による消化 | タスクの超過（AC − EV）をバッファが肩代わりしている量。操作ではなく自動で決まる |
| 未使用の枠 | 確保量のうち、取り崩しにも解放にも使っていない量 |
| バッファ残 | 未使用の枠から、現在の超過を差し引いた量 |
| 現在の必要量 | 見直しの時点で、残っている不確実性に対して必要なバッファの量 |
| 消化率 | 確保量（解放分を除く）のうち、消化した割合 |
| 出来高率 | BAC のうち、出来高（EV）の割合 |
| 当初BAC | バッファ計画の確定時点の BAC |
| バッファ計画の確定 | 承認時点の計画（確保量・当初BACなど）を記録し、以後の変化の起点にする操作 |
| リザーブ分析 | 残っている予備と、残っているリスクを比べて、バッファの過不足を判断する見直し |

## 4. 基本方針

| 項目 | 方針 |
|---|---|
| 単位 | 工数。期間（納期）のバッファは将来検討する |
| 層 | バッファと管理予備を分けられる設計にする。管理予備は当面システムでは持たない |
| BAC | **タスクだけ** で構成する。バッファは BAC に含めず、別枠で持つ |
| 置き場所 | WBS に1つ。工程ごとのバッファは持たない（工程ごとの契約や決裁は想定しない）。消化の内訳は工程別に見られるようにする |

### BACにバッファを含めない理由

バッファそのものには出来高（EV）が付かない。BAC に含めると完了率が 100% にならず、EAC などの読み方も濁る。

- 「計画どおりか」は、EAC と BAC を比べて判断する
- 「バッファで吸収できるか」は、EAC と BAC ＋ バッファを比べて判断する（9章の着地見込み）

### 工程ごとにバッファを持たない理由

- 工程ごとに分けると、まとめて持つ場合より多くの量が必要になる（リスクの共有の効果が失われる）
- 工程の中で使い切られやすく、工程単位のサバに戻る
- 問題は工程の境目を越えて現れる（例：設計の誤りがテスト工程で見つかる）

## 5. 大きさの決め方

### 明細方式

バッファの大きさは、根拠ごとの **明細の合計** として決める。数字を1つだけ入力する方式はとらない。

明細は「根拠の内訳」であり、「財布の分割」ではない。

- 超過による消化と取り崩しは、WBS全体の1つのプールから行う。どの明細から払うかは縛らない
- 解放は明細単位で行う

### 算定方法

認める算定方法は次の2つである。**方法を問わない直接入力は認めない。**

| 種別 | 計算 | 備える不確実性 |
|---|---|---|
| リスク | 発生確率 × 影響工数（期待値） | 特定済みのリスク（起きるか、起きないか） |
| 比率 | 対象工数 × 比率 | 見積もりのブレ（どのタスクにも少しずつ起きる） |

比率の対象は、WBS全体または特定の工程とする。

### 明細の項目

| 項目 | リスク | 比率 | 内容 |
|---|---|---|---|
| 内容 | 必須 | 必須 | 何に備えるか |
| リスクの記述 | 必須 | — | 原因 → 何が起きるか → どう影響するか |
| 影響工数の内訳 | 必須 | — | 起きたときに何をするか、その工数 |
| 発生確率と根拠 | 必須 | — | 高・中・低から選ぶ。根拠は一言でよい |
| 対象と比率と理由 | — | 必須 | 対象（WBS全体／工程）、比率（%）、その比率の理由 |
| 不要になる条件 | 必須 | 任意 | いつ解放を検討するか（例：「外部API仕様の確定」） |

確保量はシステムが計算する。

**不要になる条件の扱いがリスクと比率で異なる理由**

- リスクの必要量を動かすのは **PMの判断** である。PMがクローズにしない限り必要量は減らない。クローズにしてよいかの拠り所として、条件が必要になる
- 比率の必要量を動かすのは **進捗** である。比率 × 残作業 で自動的に減るため、拠り所となる条件は要らない（7.1）

### 発生確率

- 高・中・低の3段階とする。各段階の値は **システム全体で1つ** とし、プロジェクトごとには変えない（初期値は 高 70% ／ 中 40% ／ 低 10%）
- 明細には、登録時の値（%）も記録する。システム全体の値が後で変わっても、確定済みの確保量は変わらない

値をプロジェクトごとに変えられないようにするのは、総量を調整する「つまみ」にさせないためと、プロジェクト間で比べられるようにするためである。

### 入れないもの

- リスクに事前に打つ手（例：先にプロトタイプを作って仕様を詰める）の工数は、計画した作業として WBS のタスクにする。バッファに入れるのは、リスクが起きたときの対応の工数だけである
- 見積もりのブレとリスクを二重に数えない。比率の明細に個別のリスクを含めず、リスクの明細に通常のブレを含めない
- **期待値で扱えない大きなリスク** は明細にしない。目安は、影響工数がバッファ全体を超えるものである。
  - 確率が低いもの（例：低 10% × 500h）は、管理予備で備える。当面はシステムの外で管理する
  - 確率が高いもの（例：高 70% × 250h）は、事前の対応策（WBSのタスク）でリスクそのものを小さくする

### 例

タスク合計 1,000h の WBS

| 種別 | 内容 | 算定 | 確保量 |
|---|---|---|---|
| 比率 | 見積もりのブレ | 1,000h × 10%（理由：類似案件の見積もり精度が±10%程度） | 100h |
| リスク | 外部API仕様の確定遅れ | 中 40% × 80h | 32h |
| リスク | 主要メンバーの離脱 | 低 10% × 150h | 15h |
| **合計** | | | **147h** |

## 6. バッファ計画の確定

承認時点の計画を記録し、以後の変化の起点にする操作である。**基準（KIJUN）を固定する機能ではない。**

### 単位とタイミング

- WBS ごとに1回、PM が **計画の承認時** に行う
- 確定前は、明細を自由に追加・編集・削除できる
- 確定するときに、基準が未設定のタスク（予定工数で代用されるもの）があれば警告する

### 確定時に記録するもの

| 記録するもの | 内容 | 使い道 |
|---|---|---|
| 明細ごとの確保量 | 工数。リスクの明細は登録時の発生確率（%）も含む | 書き換え禁止の起点 |
| 当初BAC | 確定時点の BAC（工数と金額） | BAC が増減した理由を追う |
| 換算単価と決め方 | 例：6,000円/h（WBS平均単価） | 金額モードの換算（10章） |
| 全タスクのスナップショット | 確定時点の各タスクの基準工数・単価・フェーズ。既存の進捗スナップショットの仕組みで1回記録する | 確定後に追加・削除・変更されたタスクを特定する |
| 確定日・確定者 | | 台帳の起点 |

### 確定の前と後で変わること

| 項目 | 確定前 | 確定後 |
|---|---|---|
| バッファの明細 | 自由に追加・編集・削除 | 内容は変えない。状態（発生・クローズ）と現在の発生確率だけ、見直しで更新する |
| 確保量 | 明細の合計（未確定） | 追加・取り崩し・解放でのみ変わる |
| フィーバーチャートの判定 | 出さない（「未確定」と表示） | 出す |
| タスクと基準工数 | 自由（Excel同期・画面） | 自由。ただし当初BACとの差として見える |

### 取り消しと再確定

- 確定の取り消しは、**台帳に操作が1件もないときだけ** 認める（入力ミスの訂正用）
- 操作が1件でもあれば取り消せない。確保量を増やすなら「追加」、減らすなら「解放」を使う
- 計画の作り直し（再確定）は設けない

取り消しを限るのは、「取り消す → 確保量を書き換える → 確定し直す」という手順で、理由のない書き換えができてしまうのを防ぐためである。

### 基準（KIJUN）との関係

- 基準工数は、これまでどおり Excel（Geppo）から同期され、BAC と PV_BASE の計算に使う。確定はこれを止めない
- 確定後に基準工数が変わると、その分は当初BACとの差として現れる。基準の付け替えが見えるようになる
- 基準そのものを固定する方式（確定後は同期で基準を上書きせず、変更は承認を経て確定し直す）は、スコープ変更の記録とあわせて将来検討する

## 7. 量の変化

### 7.1 確保量と現在の必要量

2つの量を分けて持つ。

| 量 | 意味 | 変わるとき |
|---|---|---|
| 確保量 | 確定した量 | 追加・取り崩し・解放の操作のときだけ |
| 現在の必要量 | 残っている不確実性に対して必要な量 | 見直しのたびに計算し直す |

現在の必要量は次のとおり計算する。

| 種別 | 現在の必要量 |
|---|---|
| リスク（未発生） | 現在の発生確率 × 影響工数 |
| リスク（発生・クローズ） | 0（見直しの対象から外す） |
| 比率 | 比率 × 対象の残作業（対象の BAC − 対象の EV） |

発生確率を見直しても、確保量は自動では変わらない。両者の差を見て、PM が解放やエスカレーションを判断する。

### 7.2 計算式

```
確保量       = 当初確保量 + 追加累計
未使用の枠   = 確保量 − 取り崩し累計 − 解放累計
現在の超過   = max(0, 全体のAC − 全体のEV)
バッファ残   = 未使用の枠 − 現在の超過
消化量       = 取り崩し累計 + 現在の超過
消化率       = 消化量 ÷ (確保量 − 解放累計) × 100
出来高率     = EV ÷ BAC × 100        … BAC はタスクだけ（取り崩しで追加したタスクを含む）
```

- 超過は WBS 全体の合計で見る。早く終わったタスクの余りは、他のタスクの超過と相殺される
- 取り崩した分はタスクの BAC に入るので、その分だけ超過が小さくなる。取り崩しと超過は二重に数えない
- 解放は「使った」のではなく「不要になった」ものなので、消化量に数えない

### 7.3 追加

決裁変更を経て、確保量を増やす操作である。

- 決裁変更そのものはシステムの外で行う
- 追加分は、根拠つきの **新しい明細** として登録する（5章の算定方法に従う）
- 記録する項目：日付、工数、理由、承認者、承認日、登録者

追加を操作として記録するのは、消化率が下がった理由を説明できるようにするためである。確保量を直接書き換えると、同じ変化が理由なしに起き、プロジェクトが持ち直したように見えてしまう。

### 7.4 取り崩し

**大原則：取り崩しは、これから行う作業に充てる。すでに起きた超過の穴埋めには使わない。**

超過したタスクにバッファから予算を足すと、超過が帳簿から消え、CPI が良く見えて性能の問題が隠れる。超過分は、超過による消化として、バッファが肩代わりしていることが見えたままにする。

| ケース | 例 | 扱い |
|---|---|---|
| 見積もりのブレ | 100h の実装が 130h かかっている | 取り崩さない。超過による消化として見える |
| リスクの発生 | 外部API仕様が遅れて確定し、連携部分の作り直しが必要になった | 取り崩す |
| 計画漏れ | 合意した範囲内なのに、データ移行の作業が WBS に無かった | 取り崩す |
| スコープの追加 | 顧客から画面の追加を依頼された | 取り崩さない（8章） |

- 取り崩しは **新しいタスクを追加するときに限る**。既存タスクの予算は増やさない（「作業が増えた」と「長引いた」の区別を保つため）
- 理由が「リスクの発生」のとき、対象のリスク明細の状態を「発生」にする

**上限**

| 取り崩す量 | 扱い |
|---|---|
| バッファ残以内 | 取り崩せる |
| バッファ残を超え、未使用の枠以内 | 警告を出したうえで取り崩せる。エスカレーションを促す |
| 未使用の枠を超える | 取り崩せない。先に「追加」で確保量を増やす |

バッファ残を超える場合を止めないのは、リスクが起きて作業が必要なのは事実で、止めても作業は消えないためである。また、現在の超過は今後の作業で縮むこともある。記録して進め、危険信号を正しく出す方がよい。

**記録する項目**：日付、工数、理由の区分（リスクの発生／計画漏れ）、対象のリスク明細（リスクの発生なら必須）、追加したタスク、説明、判断者（PM）

### 7.5 見直しと解放

**見直し（リザーブ分析）**

PM が、工程の区切りと、リスクがクローズしたときに行う。

```
残っている予備   = バッファ残
残っているリスク = Σ(未発生のリスク明細：現在の発生確率 × 影響工数)
                 + Σ(比率の明細：比率 × 対象の残作業)
```

| 結果 | 条件の目安 | 対応 |
|---|---|---|
| 維持 | 残っている予備と残っているリスクが見合っている | なし |
| 解放 | 残っている予備が多すぎる | 不要な分を解放する |
| 不足 | 残っている予備が足りない | 上位者へエスカレーションする（必要なら追加） |

**解放**

- 明細単位で行う。自動では行わない（PM が根拠をもって判断する）
- 記録する項目：日付、工数、対象の明細、理由、行き先、判断者
- 行き先は「見込み利益の上方修正」とする（管理予備を持たないため）

解放が必要な理由は次のとおりである。

- 根拠（リスク）が消えた予備を残すと、理由のない余裕になり、作業が膨らむ
- 消化率の分母が実態より大きいと、超過が進んでいても判定が「健全」のまま出続ける
- 使わないと分かっている予備を抱えたままだと、最終原価の見込みが実態より高く見え続ける

早すぎる解放は避ける。工程が終わっても、その工程で作り込んだ不具合は後で表に出るため、WBS全体にかかるリスクの分は残す。

## 8. スコープ変更との関係

### 線引き

判断の基準は、**合意した成果物・要件の範囲が変わるか** である。

| ケース | 範囲 | 扱い |
|---|---|---|
| 顧客からの追加依頼（有償） | 範囲外 | 変更管理 → 契約変更 → 決裁額の増額 |
| 範囲外だが無償で受ける | 範囲外 | 変更管理 → 決裁変更（利益が減ることを、利益に責任を持つ人が承認） |
| 解釈が食い違った末、元々範囲内と判断 | 範囲内 | スコープ変更ではなく計画漏れ。バッファから取り崩す |
| 自社の判断による作り込み | 範囲外 | 原則やらない。必要なら変更管理に乗せる |

スコープ追加をバッファから払わない理由は次のとおりである。

- 無償で受けるのは利益を減らす商売上の判断であり、PM が持つ実行上の備えで代行すべきではない
- 元の範囲のリスクへの備えが、誰も決めないまま減る
- スコープ変更があったことが記録から消える

### 当面の扱い

- スコープ変更の記録の機能は将来に回す。当面、スコープ追加は **通常のタスク追加** として扱い、バッファには触れない
- スコープ追加で BAC が増えると出来高率が下がり、成績が同じでも判定は厳しく出る。これは仕様とする（同じバッファでより多くの作業を守ることになるため）
- 取り崩し以外で BAC が当初より増えているときは、画面に注記を出す
  - 例：「BACが取り崩し以外で当初より200h増えています。追加した範囲のバッファを足していない場合、判定は厳しめに出ます」
- 追加した範囲の分のバッファは、「追加」（7.3）で足せる

## 9. 監視と表示

### 監視で答える問い

| 問い | 見るもの |
|---|---|
| 減り方は健全か（ペース） | フィーバーチャート（軌跡） |
| 最後まで足りるか（着地） | 完了時のバッファ残見込み |
| 何が減らしているか（原因） | 消化の内訳 |
| 備えは今のリスクに見合っているか（見直し） | リザーブ分析（7.5） |

### フィーバーチャート

横軸に出来高率、縦軸に消化率をとり、確認日ごとの点を線でつないだ **軌跡** で判断する。開始直後の1点はぶれやすいため、方向を見る。

**判定**

| 判定 | 条件 |
|---|---|
| 危険 | 消化率 ≧ 100% |
| 健全 | 消化率 ≦ 出来高率 ＋ 健全の境界 |
| 注意 | 消化率 ≦ 出来高率 ＋ 危険の境界 |
| 危険 | 上記のいずれにも当たらない |

上から順に判定する。健全の境界と危険の境界はプロジェクト設定で調整できる（初期値は 0pt と 20pt。現行の基準と同じ）。

### 着地見込み

```
完了時のバッファ残見込み = 未使用の枠 − max(0, EAC − BAC)
```

マイナスなら、今の効率のままでは足りない。エスカレーションを検討する合図とする。

### 消化の内訳

| 内訳 | 粒度 |
|---|---|
| 超過 | 工程別（各工程の AC − EV）。工程ごとの値の合計は全体の超過と一致させる |
| 取り崩し | 理由別（リスクの発生／計画漏れ）、リスク明細別 |
| 解放 | 履歴として表示する（消化には数えない） |

### 表示する場所

| 場所 | 内容 |
|---|---|
| プロジェクト概要 | 判定と、バッファ残 |
| EVMダッシュボード | フィーバーチャート（軌跡）、着地見込み、消化の内訳、BAC 増加の注記（8章） |
| バッファの明細画面 | 明細の一覧（確保量・解放済み・現在の必要量）、リザーブ分析、確定・追加・取り崩し・解放の操作と台帳 |

フェーズを指定した EVM では、バッファを扱わない（バッファはフェーズに属さないため）。

## 10. 金額モード

基本の単位は工数とし、金額は換算して表示する。

| 量 | 金額への換算 |
|---|---|
| 確保量・追加・解放 | 工数 × 確定時の換算単価 |
| 取り崩し | 追加したタスクの金額（工数 × そのタスクの単価）。BAC に入る金額と一致させる |
| 超過 | AC − EV（金額） |

- 換算単価は確定時に決めて固定し、記録する。決め方は「WBS平均単価（担当者が未登録ならデフォルト単価）」か「デフォルト単価」から選ぶ
- 固定するのは、担当者の入れ替わりで WBS 平均単価が変わったときに、何も起きていないのにバッファの金額や消化率が動くのを防ぐためである
- 単価の高い担当者のタスクに取り崩すと、金額では工数以上にバッファが減る。原価の見方としては正しい動きである
- 現行の「BACに含めない」の選択肢は廃止する（バッファは常に BAC に含めないため）

## 11. 設定一覧

| 設定 | 範囲 | 初期値 |
|---|---|---|
| 発生確率の値（高・中・低） | システム全体 | 70% ／ 40% ／ 10% |
| 判定の境界（健全・危険） | プロジェクト | 0pt ／ 20pt |
| 換算単価の決め方 | プロジェクト（確定時に適用） | WBS平均単価 |

## 12. 未決事項と将来機能

### 未決事項（次の論点：現行システムとの対応付け）

| 事項 | 内容 |
|---|---|
| 既存データの移行 | 現行の `wbs_buffer`（名前・工数・種別 RISK/OTHER のみで根拠を持たない）をどう扱うか |
| Excelのタスク単位のバッファ工数 | Geppo の `KIJUN_KOSU_BUFFER` は、同期時に `task_kosu`（種別 RISK）として取り込まれているが、どこにも使われていない。タスクに上乗せした形のバッファをどう扱うか |
| Excel同期と取り崩しのタスク | 現行の差分同期は、Excel にないタスクを論理削除する（画面から追加したタスクも対象）。取り崩しで追加したタスクも、Excel に同じタスクNoで追加しないと次の同期で消える。取り崩しの記録とタスクの紐付け方を決める |
| バッファ計画の確定の実装 | 進捗スナップショットの流用方法、当初BACの持ち方 |
| 既存仕様書の改訂 | `docs/specs/02-evm.md` の「9. バッファの取り扱い」など、実装に合わせて改訂する |

### 将来機能

| 機能 | 内容 |
|---|---|
| スコープ変更の記録 | 変更の内容・有償か無償か・承認者・承認日・追加工数を記録し、追加タスクと紐付ける。BAC の増分を理由ごとに説明できるようにする |
| 基準の固定 | 確定後は同期で基準を上書きせず、変更は承認を経て確定し直す。スコープ変更の記録とあわせて検討する |
| 管理予備 | 範囲内の想定外への備え。期待値で扱えない大きなリスクの置き場所にもなる |
| 期間（納期）のバッファ | マイルストーンの話としてあわせて検討する |
| 過去実績による比率の提案 | 類似案件の基準工数と実績から、比率の明細の比率を提案する |
| 三点見積 | タスクごとの楽観・最頻・悲観の見積もりから、見積もりのブレを統計的に求める |

## 13. 現行実装との差分

| 項目 | 現行 | 本仕様 |
|---|---|---|
| BAC | タスクの基準工数 ＋ バッファ | タスクの基準工数だけ |
| バッファの登録 | 画面がない（シードまたはDB直接） | 明細画面から登録。確定後は操作でのみ変わる |
| バッファの中身 | 名前・工数・種別（RISK/OTHER）。根拠を持たない | 明細（リスク／比率）ごとに根拠を持つ |
| 大きさの決め方 | 数字の直接入力 | リスク期待値か比率。直接入力は不可 |
| 確定 | なし | バッファ計画の確定 |
| 減り方 | 超過（AC − EV）のみ | 超過による消化・取り崩し・解放、と追加 |
| 判定の境界 | 固定（0pt ／ 20pt） | プロジェクト設定で調整（初期値は同じ） |
| 金額換算 | 計算のたびに WBS平均単価などで換算。BACに含めない選択肢あり | 確定時の単価で固定。BACに含めない選択肢は廃止 |
| 表示 | EVMダッシュボードのカードのみ。WBS画面は取得しているが表示していない | プロジェクト概要・EVMダッシュボード・バッファの明細画面 |

## 付録：計算例

前提

- 当初BAC 1,000h、確保量 170h
- 外部APIのリスクが発生し、80h を取り崩して新しいタスクを追加した（BAC 1,080h）
- 現在 EV 540h、AC 575h

| 量 | 計算 | 結果 |
|---|---|---|
| 現在の超過 | max(0, 575 − 540) | 35h |
| 未使用の枠 | 170 − 80 − 0 | 90h |
| バッファ残 | 90 − 35 | 55h |
| 消化率 | (80 + 35) ÷ 170 | 67.6% |
| 出来高率 | 540 ÷ 1,080 | 50.0% |
| 判定 | 67.6% は 50.0% ＋ 20pt 以内 | 注意 |
| EAC（CPI方式） | 1,080 ÷ (540 ÷ 575) | 1,150h |
| 完了時のバッファ残見込み | 90 − max(0, 1,150 − 1,080) | 20h |

ここからスコープを 200h 追加した場合（通常のタスク追加）

| 量 | 計算 | 結果 |
|---|---|---|
| 出来高率 | 540 ÷ 1,280 | 42.2% |
| 判定 | 67.6% は 42.2% ＋ 20pt を超える | 危険 |
| 追加した範囲のバッファを追加（200h × 10% ＝ 20h）した後の消化率 | 115 ÷ 190 | 60.5%（注意） |

取り崩しの上限（上記の取り崩し直後の状態）

| 取り崩す量 | 扱い |
|---|---|
| 40h | 取り崩せる（バッファ残 55h 以内） |
| 70h | 警告を出したうえで取り崩せる（未使用の枠 90h 以内） |
| 100h | 取り崩せない（未使用の枠 90h を超える） |
