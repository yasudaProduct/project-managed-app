## 1. 前提（このアプリの運用モデル）

整理は以下の運用を前提にする。前提が違う場合は §8 で確認する。

| 項目 | 前提 |
|---|---|
| 開発スタイル | 工程（フェーズ）を順に進めるウォーターフォール型 |
| 計画の入力元 | Excel → Geppo MySQL → 本アプリへ WBS 同期（定期インポート可） |
| 計画の種類 | 基準（KIJUN＝ベースライン）と予定（YOTEI＝現行計画）の2本を持つ |
| 実績の入力元 | Geppo 月報（月報システム → MySQL へは1時間ごとに反映）。本アプリ（PostgreSQL）への取込は未運用で、頻度は §7.1 の案で決める |
| 利用者 | 主に PM。管理者・PMO・作業者も閲覧する |
| 進捗確認のサイクル | 案件ごとに異なる（日次〜月次） |
| 進捗の入力 | タスクのステータス・進捗率（Excel 側で更新し同期、またはアプリで編集） |
| 余裕 | WBS バッファ（`WbsBuffer`）を工数で持つ。現状は BAC に加算されるだけ |

## 2. 進捗管理で答えるべき問い

進捗管理は「指標を出すこと」ではなく、**PM が次の行動を決めるために答えるべき問い**に答えることが目的。機能はこの問いに対応づけて設計する。

| # | 問い | 分析の種類 | 主な指標・ビュー |
|---|---|---|---|
| Q0 | **この数字は信用できるか** | データ品質・鮮度 | 最終同期日時、実績取込済み期間、未入力・未紐付けデータ |
| Q1 | 予定どおり進んでいるか | 現状把握（スケジュール） | SPI / SV、遅延タスク、イナズマ線 |
| Q2 | 工数（予算）内に収まっているか | 現状把握（コスト） | CPI / CV、工数超過タスク、月別予実 |
| Q3 | 計画そのものは変わっていないか | 現状把握（スコープ） | 基準と予定の差、BAC の推移 |
| Q4 | どこが原因か | 原因特定（ドリルダウン） | フェーズ別・タスク別の差異、影響度順の並び |
| Q5 | このままだとどこに着地するか | 予測 | EAC / VAC / TCPI、予測完了日、マイルストーン達成見込み |
| Q6 | 何をすべきか | 対策判断 | 担当者負荷、バッファ残、再スケジュール試算 |
| Q7 | 次のプロジェクトに何を活かすか | 振り返り | フェーズ別・作業種別の見積精度 |
| Q8 | 組織として、どのプロジェクトが危ないか | 横断（ポートフォリオ） | 全プロジェクトのヘルス一覧、横断負荷 |

Q0 は他のすべての前提。数字を信用できないと、どの分析も使われなくなる。

## 3. 利用者と頻度（運用シナリオ）

| タイミング | 主な利用者 | 見たいこと | 対応する問い |
|---|---|---|---|
| 日次 | メンバー、リーダー | 今日・今週の期限、自分の遅れ、過負荷 | Q1, Q6 |
| 週次（進捗会議） | PM、リーダー | 全体の SPI/CPI、遅延タスク上位、原因フェーズ、今週の対策 | Q0〜Q6 |
| 月次（実績取込後） | PM、管理者 | 実績確定後の CPI・EAC、月別予実、バッファ残 | Q2, Q3, Q5 |
| フェーズ完了時 | PM | そのフェーズの見積精度、次フェーズへの影響 | Q4, Q5, Q7 |
| プロジェクト完了時 | PM、PMO | 見積精度の振り返り、ナレッジ化 | Q7 |
| 随時 | 管理者、PMO | 危ないプロジェクトの把握、要員の横断調整 | Q8 |

進捗会議のサイクルは案件ごとに日次〜月次で異なるため、上表の「週次」は案件のサイクルに読み替える。サイクルの違いの吸収方法は §4 原則 7 を参照。

## 4. 分析設計の原則

1. **比率と絶対値をセットで出す。** SPI 0.5 でも PV 2h なら影響は小さく、SPI 0.9 でも PV 200h なら 20h の遅れ。影響度は SV/CV（絶対値）で並べる。
2. **現在値より推移。** 「悪い」より「悪化し続けている」の方が手を打つ判断に直結する。
3. **次の行動につながる指標だけを載せる。** 見て終わりの指標は増やさない。
4. **数字の鮮度と信頼性を常に添える。** 実績は月報取込でしか増えないため、取込の間は EV だけが伸びて CPI が実態より高く出る。評価日・取込済み期間を画面に出す。
5. **担当者別は支援判断のために使い、個人評価には使わない。** 見積は本人が作っていないことが多く、また評価に使うと進捗率の水増しや実績の過少計上が起きて、全体のデータが壊れる。
6. **フェーズ完了後の SPI は見ない。** 完了すると EV = PV = BAC で必ず 1.0 になる。完了フェーズは CPI（見積精度）で評価する。
7. **期間の単位を固定しない。** 進捗確認のサイクル（日次／週次／月次）をプロジェクト設定に持ち、以下の既定値をそこから決める。画面では都度変更できる。
   - 時系列グラフの間隔と表示期間（日次なら「日次・過去1ヶ月」、月次なら「月次・全期間」など）
   - 「前回からの変化」の比較基準（前日／前週／前月）
   - 通知のまとめ方（日次まとめ／週次まとめ）
   - トレンド悪化検知の「N 期連続」の期の単位
   - データの更新頻度はサイクルに連動させず、全案件で日次以上にそろえる（§7.1）

## 6. 主なギャップ（重要度順）

1. **遅延・超過を「見つける」仕組みがない。** EVM の全体値とイナズマ線はあるが、「どのタスクが何日遅れているか」の一覧がなく、通知の遅延・工数超過検知も仮実装のまま。週次進捗会議の中心になる情報が欠けている。
2. **数字の鮮度が分からない。** 実績が月報取込でしか増えないため、取込の間は CPI が高めに出る。いつ時点の数字かが画面から分からない。
3. **原因箇所の影響度が分からない。** 内訳は比率（SPI/CPI）だけで、影響の大きさ（SV/CV）で並べられない。
4. **推移が全体しかない。** 「どのフェーズが悪化し続けているか」が見えない。
5. **着地点の判断材料が足りない。** TCPI、バッファ残、マイルストーン達成見込みがない。
6. **組織としての一覧がない。** 危ないプロジェクトを探すには WBS を1つずつ開く必要がある。

## 7. 機能追加ロードマップ案

規模の目安: S（数日）/ M（1〜2週）/ L（それ以上、スキーマ変更を含む）

### 7.1 実績取込の運用案（開発不要）

既存の WBS 定期インポート（`WbsImportSchedule`）の「実績も取り込む」（`includeActuals`）を有効にし、**毎日1回以上**実行する。

- WBS 同期（EV 側）と月報取込（AC 側）が同じタイミングで更新されるため、CPI が食い違わない。別々のタイミングで取り込むと、片方だけ進んだ状態の CPI を見ることになる
- MySQL 側は1時間ごとに更新されるが、日次の朝会でも前日分までそろえば足りるため、毎時は不要。日次で朝会を行う案件は朝会前（例: プリセット「毎日 9時・12時・17時」）に取り込む
- ただし、**実績の鮮度を最終的に決めるのは作業者の月報入力のタイミング**。月末にまとめて入力する運用だと、毎日取り込んでも月の途中の AC は少なく、CPI が高めに出る。このため 1-4 では「取込日時」より「実績が入力済みの最終日」を表示する

### Step 1: 進捗会議で使える状態にする（既存データのみで実現）

| # | 機能 | 答える問い | 規模 | 補足 |
|---|---|---|---|---|
| 1-0 | **進捗確認サイクルのプロジェクト設定**（日次／週次／月次）と、時系列の既定間隔・表示期間への反映 | ― | S | §4 原則 7。1-5・3-3・通知が参照する |
| 1-1 | **遅延タスク一覧**：予定終了日超過で未完了／予定開始日超過で未着手のタスクを、遅延日数・担当者・フェーズ・クリティカルパス該当つきで一覧。担当者で絞り込める（作業者が自分の分を見る用途） | Q1, Q4 | M | 判定ロジックはドメインに置き、1-2 と共用する |
| 1-2 | **通知の検知ロジック本実装**（スケジュール遅延・工数超過・期限警告の仮実装部分） | Q1, Q2 | M | プロジェクト設定の `deadlineAlertDays` / `costOverrunThresholdPct` を使う |
| 1-3 | **EVM 内訳の拡張**：SV / CV 列の追加、影響度順ソート、TCPI の算出 | Q4, Q5 | S | |

### Step 2: 悪化箇所と着地点を見る

管理者・PMO も閲覧するため、3-1（ポートフォリオ一覧）は Step 2 の最初に前倒しする。

| # | 機能 | 答える問い | 規模 | 補足 |
|---|---|---|---|---|
| 2-1 | **EVM グラフのフェーズ切り替え**（全体／フェーズ別の系列）とフェーズ別の予測完了日 | Q4, Q5 | L | スナップショット記録時にフェーズ ID を保存する。現在のフェーズを結合して復元する方式は、タスクのフェーズ移動で過去値が変わるため採らない |
| 2-2 | **バッファ消化管理**：バッファ消化率（超過工数 / バッファ）と出来高率の対比 | Q5, Q6 | M | 消化率が進捗率を大きく上回ったら警告 |

| # | 機能 | 答える問い | 規模 | 補足 |
|---|---|---|---|---|

| 3-2 | **見積精度分析**：フェーズ別・作業種別の「実績 / 基準」比、プロジェクト横断の比較 | Q7 | M | |
| 3-3 | **トレンド悪化の検知**：SPI / CPI が N 期連続で悪化したら通知 | Q1, Q2 | S | 2-1 の後に実施 |

### 優先しないもの

- **担当者別 EVM の推移**：サンプルが小さく指数が振れやすい。帰属も「現担当者」基準でずれがある。担当者軸は負荷ヒートマップと遅延タスク一覧（担当者で絞り込み）で十分と判断する。

## 8. 確認したい事項

回答済み（2026-10-31）:

- 主な利用者 → PM。管理者・PMO・作業者も閲覧する（3-1 を前倒し、1-1 に担当者絞り込みを追加）

- 月報の取込頻度 → MySQL へは1時間ごと。本アプリへの取込は未運用（§7.1 の運用案を追加）

未回答:

1. **作業者の月報入力のタイミング**：毎日入力か、週末・月末にまとめて入力か（§7.1。1-4 の表示内容に影響）

3. **マイルストーンの粒度**：「フェーズ完了＝マイルストーン」でよいか、フェーズとは別に管理するか（2-3 の設計が変わる）。

   - リスク・課題管理（データモデルなし）
   - 品質指標（不具合数、テスト消化など）
   - 変更管理ワークフロー（変更要求の起票・承認）
   - 遅延・超過の要因分類（見積誤り／仕様変更／待ち など）
