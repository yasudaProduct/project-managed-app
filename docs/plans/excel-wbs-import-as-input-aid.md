# 計画書: ExcelのWBSを「同期」から「入力補助のインポート」に切り替える

> **ステータス：方針決定・未着手**
> 改修は別ブランチで行う。改修が終わるまでの暫定運用は「8. 暫定運用」に従う。
> 関連：`docs/specs/15-buffer.md`（バッファ管理仕様書）

## 1. 背景と目的

### これまで

ExcelのWBS（Geppo の MySQL を経由）を正とし、差分同期・洗い替え・定期実行でシステムに反映してきた。もともと Excel で WBS を運用していた状態からシステムを作ったこと、慣れた Excel の方がタスクや予定を編集しやすいことが理由である。

### 問題

- システムは変更を **検知はできても、止めることも理由を聞くこともできない**。基準の付け替えやスコープ追加も、同期で結果だけが入ってくる
- 差分同期は Excel を唯一の真実源として、タスク名・担当者・状態・進捗・期間を毎回上書きする。**システム（ガント）での編集は次の同期で消える**
- Excel では、同じタスクのタスクNoだけを変えることもできる。システムからは「削除＋追加」に見え、作業実績・依存関係・履歴とのつながりが切れる
- バッファの確定や取り崩し（`docs/specs/15-buffer.md`）と両立しない。例えば、システムで追加したタスクは、Excel にないため次の差分同期で論理削除される

### 目的

タスク（WBS）の正をシステムに移す。ExcelのWBSは、初回作成のための入力補助として扱う。

## 2. 方針（決定事項）

| 項目 | 方針 |
|---|---|
| タスク（WBS）の正 | **システム** |
| ExcelのWBS | 初回作成のための入力補助。「同期」ではなく「インポート」と呼ぶ |
| 月報（実績工数） | **Excelが正のまま**。定期インポートも残す |
| 定期インポート | WBSは廃止する。月報だけを定期実行する |
| 差分インポート・洗い替えインポート | 残す。破壊的な変更になり得るため、プレビューと注意事項を出してから実行する |
| Excelのタスク単位のバッファ工数（`KIJUN_KOSU_BUFFER`） | 取り込まない |

## 3. インポートのルール

インポートの扱いは、WBSの「バッファ計画の確定」（`docs/specs/15-buffer.md` 6章）の前と後で変える。確定は承認時点の計画を記録する操作であり、それ以降の変更こそ管理したいものだからである。

### 3.1 確定の前と後

| | 確定前（計画中） | 確定後（実行中） |
|---|---|---|
| 差分インポート | できる。Excel にないタスクは削除する（プレビューで確認） | できる。ただし次の制限がある<br>・取り込むのは計画の項目だけ（3.3）<br>・削除は、プレビューで選んだものだけ（既定は削除しない）<br>・取り崩しに紐付いたタスクは、変更も削除もしない |
| 洗い替えインポート | できる（注意を表示する） | **できない**。台帳の操作が0件なら、確定を取り消してから行う |
| 定期インポート | 廃止 | 廃止 |

### 3.2 プレビューと注意事項

インポートは、プレビューで内容を確認してから実行する。

| 示すこと | 確定前 | 確定後 |
|---|---|---|
| 追加・削除・変更の件数と、工数の増減 | ○ | ○ |
| 削除されるタスクのうち、作業実績があるもの・依存関係を持つもの | ○ | ○ |
| タスクNoの付け替えの疑い（名前と工程が同じで、タスクNoだけが違う） | ○ | ○ |
| タスクNoの形式（工程コード-4桁の連番）から外れるもの | ○ | ○ |
| 当初BACとの差への影響 | — | ○ |
| 取り込まない項目（進捗・状態、既存タスクの基準など） | — | ○ |
| 取り崩しに紐付いていて、対象外になるタスク | — | ○ |

洗い替えでは、次のものが失われることを明示する（現行の実装を確認済み）。

- タスクを物理削除して作り直すため、タスクのIDが変わる
- 依存関係が消える
- 作業実績とタスクの紐付けが外れる（`WorkRecord.taskId` が NULL になる）
- そのWBSの進捗スナップショットがすべて削除される

### 3.3 取り込む項目

| 項目 | 確定前 | 確定後（既存のタスク） | 確定後（新しいタスク） |
|---|---|---|---|
| タスク名・工程・担当者 | 取り込む | 取り込む | 取り込む |
| 予定（日程・工数） | 取り込む | 取り込む | 取り込む |
| 基準（日程・工数） | 取り込む | **取り込まない** | 取り込む |
| 状態・進捗率 | 取り込む | 取り込まない | 取り込まない（未着手・0%で作る） |
| 実績日 | 取り込む | 取り込まない | 取り込まない |
| タスク単位のバッファ工数（`KIJUN_KOSU_BUFFER`） | 取り込まない | 取り込まない | 取り込まない |

確定後に既存タスクの基準を取り込まないのは、承認された計画の基準を一括の取り込みで変えられないようにするためである。確定後に基準を変えたい場合は、システムで1件ずつ変える。変えた分は、当初BACとの差として見える。

### 3.4 実行の記録

インポートごとに、実行日時・実行者・モード（差分／洗い替え）・内容の要約（追加・削除・変更の件数）を記録する。

## 4. タスクNo

タスクNoは、システムとExcelの月報をつなぐ共通のキーになる。月報の実績は「プロジェクトID＋タスクNo（`WBS_NO`）」でタスクに紐付く（`src/applications/geppo-import/geppo-import-application-service.ts`）。

| 方針 | 内容 |
|---|---|
| 体系 | 「工程コード-4桁の連番」（例：D1-0001）に統一する。インポートで体系から外れる番号は、プレビューの注意事項として示す（取り込みは止めない） |
| 誰が付けるか | インポートで作るタスクは Excel の番号、システムで作るタスクはシステムの採番。システムの採番は、WBS 内で同じ工程コードを持つ番号の続きになる |
| 変えない | 一度作ったタスクNoは変えない。システムには番号を変える画面がない。Excel で番号を付け替えた場合は「削除＋追加」として扱い、プレビューで警告する |
| 再利用しない | 採番は、論理削除済みのタスクも含めた最大の番号＋1とする（[#80](https://github.com/yasudaProduct/project-managed-app/pull/80) で対応済み） |
| 月報 | 月報には、このタスクNoで実績を入力する。取り崩しで作ったタスクも同じ |

**解消した不具合**：以前のシステムの採番（`src/applications/task/task-factory.ts`）は、論理削除済みのタスクを数えなかった。一方、DBの一意制約（WBS＋タスクNo）は論理削除済みのタスクも対象である。そのため、工程の中で一番大きい番号のタスクが論理削除されていると、同じ番号を採番してタスクの作成に失敗していた。[#80](https://github.com/yasudaProduct/project-managed-app/pull/80) で、WBS 内（論理削除済みを含む）の同じ工程コードの番号から採番するように直した（`develop` にマージ済み）。

## 5. システムでの入力

| 項目 | 現状 | 改修後 |
|---|---|---|
| 基準（日程・工数） | 画面では入力できない（作成・編集とも予定・状態・進捗率だけ。基準の更新処理はコメントアウトされている） | 画面で入力・変更できる。確定前は自由。確定後も変更でき、変えた分は当初BACとの差として見える |
| 取り崩しで作るタスク | — | 基準工数を取り崩し量に、基準日程を入力した予定日程にして自動で作る（`docs/specs/15-buffer.md` 7.4） |
| 実績日 | 画面では入力できない（Excel から取り込んだ値だけ） | 未決（10章） |

## 6. 定期インポートの作り替え

### 現状

- 定期実行の設定（`WbsImportSchedule`）はWBSごとにあり、cron 式・同期モード（差分／洗い替え）・「実績も取り込む」（`includeActuals`）を持つ
- 実行すると、必ずWBSのインポートジョブを作り、「実績も取り込む」が有効なら月報（GEPPO）のジョブも作る（`src/applications/import-schedule/import-schedule-application-service.ts`）
- 月報だけを定期実行する設定はない

### 改修

- WBSのインポートジョブを作らないようにし、**月報だけを定期実行する**設定に作り替える。同期モードの項目は廃止する
- 既存の設定は、「実績も取り込む」が有効なものを月報の定期実行として残し、無効なものは無効化する
- 設定の単位（今のWBSごとのままにするか、全体にするか）は改修時に決める

## 7. バッファ機能との依存関係

| 依存 | 内容 |
|---|---|
| 確定の状態 | インポートは、WBSのバッファ計画が確定済みかどうかを参照し、3.1 のルールを切り替える |
| 取り崩しで作ったタスク | インポートでは変更も削除もしない |
| 確定時のスナップショット | 確定後は洗い替えを禁止し、確定時のスナップショットや取り崩しの紐付けを消さない |
| 実装の順番 | インポートの改修がバッファ機能より先に入る場合、確定の仕組みがまだないので、すべてのWBSを「確定前」として扱う |

## 8. 暫定運用（改修が終わるまで）

### 周知する内容

1. **ExcelからのWBSインポートは使わない。** 手動・定期とも使わず、WBSの定期インポートの設定は無効にする
2. **月報は手動でインポートする。** WBSの定期インポートを止めると、月報の定期取り込みも一緒に止まるため、作業実績のGeppo取り込み画面から取り込む
3. **画面では基準（KIJUN）と実績日を入力できない。** 新しく作るタスクには基準が入らず、BACには予定工数で計上される

### 解消した不具合

工程の中で一番大きい番号のタスクが論理削除されていると、その工程に画面からタスクを作れない不具合があった（4章）。[#80](https://github.com/yasudaProduct/project-managed-app/pull/80) で修正した。本番に反映されるまでは、この点も周知に含める。

`KIJUN_KOSU_BUFFER` を取り込まないようにした後、すでに保存されている種別 RISK の工数は、移行作業なしで消える。インポートは期間を作り直し、工数は期間と一緒に削除される（`TaskKosu` の `onDelete: Cascade`）ためである。論理削除済みのタスクには残るが、どこからも読まれない。
